# 项目执行卡死排查：pending 到永远

> 触发场景：`./scripts/verify_agent.sh` 提交任务后 poll 到 540s 仍未完成（手动 Ctrl-C）；
> 随后 `./scripts/verify_project_e2e.sh`（不经过 agent 的老路径）也卡在 pending。
> 结论：**不是 agent 的回归**，而是「执行层静默卡死 + 全链路零观测」。
> 本文记录现象、链路分段、已修复的缺陷、以及下次怎么在 5 分钟内定位。

## 1. 为什么现象永远是 pending

`submit_project` 返回的 `task_id` 只证明三件事：本地目录打包成 tar 成功、选到了目标执行节点、命令进了 swarm 队列。
**它不证明请求发出去了，也不证明有人在跑。**

链路上任何一处失败，最终都表现为 agent 看到的那一个 `pending`：

| # | 阶段 | 位置 | 失败形态 |
|---|---|---|---|
| 1 | agent 规划/打包 | `crates/agent/src/main.rs` | 本地报错，不会卡 |
| 2 | IPC 提交 + 选执行节点 | `crates/node/src/ipc/handler.rs` → `project_client.rs` | resolve_peer 失败会返回 JSON-RPC error（可见） |
| 3 | `SwarmCommand::SendProjectTask` | `crates/p2p/src/swarm.rs` | 入队成功但请求发不出去：只在 server 端 `warn!(OutboundFailure)` |
| 4 | 对端事件循环接收 | `swarm.rs:handle_project_exchange` | 曾：无 executor 时**直接 return，不发响应** |
| 5 | 执行器 + qlean | `project_executor.rs` / `sandbox/src/qlean.rs` | image/boot/upload/exec 全部无超时，永久阻塞 |
| 6 | 结果回传 | `bootstrap.rs` `ProjectResultReceived` | 没回传就永远没有结果记录 |

## 2. 本轮定位到的真实缺陷

### 缺陷 A（最致命）：执行 inline 在 swarm 事件循环上

`handle_project_exchange` 里直接 `executor.run(request).await`。项目执行是分钟级（冷启动 VM + apt 装工具链），
期间**该节点的整个事件循环停摆**：descriptor 交换、raft 消息、blob 分发全部冻结，连承载响应的那条连接都可能被
idle 超时（60s，`swarm.rs` 的 `with_idle_connection_timeout`）掐掉。

第三轮「spawn + await oneshot」的写法**并不能解决**这个问题：`ResponseChannel` 只是一个投递给
request-response handler 的 sender，响应必须由事件循环再次 poll swarm、调用
`Behaviour::send_response` 才写得出去。只要事件循环停在这个 await 上，响应就发不出去。

修复：把 ResponseChannel 登记到 `pending: HashMap<TaskId, ResponseChannel<ProjectResult>>`，
项目任务在 detached task 上执行，结束后把结果经 channel 回投事件循环，由事件循环统一
`send_response`。回归测试 `project_execution_does_not_block_the_swarm_event_loop` 用「慢执行器执行期间
第三个请求必须被及时响应」来锁死这个不变量（已验证：把执行改回阻塞式，该测试立刻失败）。

### 缺陷 B：无 executor 的节点静默丢包

`if let Some(executor) = project_executor` 没有 else 分支：没有执行器的节点会收下请求、什么都不做、
既不响应也不报错。master 一直等到协议超时（1800s）。
修复：立刻回 `exit_code=101` + 明确原因，并 warn（测试 `project_task_without_executor_is_rejected`）。

### 缺陷 C：执行层零超时

`Image::new` / `Machine::init` / `vm.upload` / `vm.exec` 都没有超时；`timeout_ms` 只在命令之间做软检查，
单条卡住的命令（apt-get 无网、guest 重启）永远不会返回，且独占唯一的 qlean worker 线程。
修复：image 300s / boot 600s / upload 300s / build+run 按剩余预算，超时明确报错并丢弃 VM（下次重建）。

### 缺陷 D：能力声明与真实执行能力不一致

节点只要配置里写了 `project_sandbox: true` 就会这样注册，而路由只看这个字段；
真正决定能否执行的是 `make_project_executor()` 是否返回 Some。
修复：拿不到可用沙箱时，注册前把 `project_sandbox` 降级为 false 并 warn。

### 缺陷 E：master 侧无兜底

`fetch_project_result` 只有「有结果」和「pending」两种答案，且 `ProjectClient` 不追踪已发出的任务。
请求即使被对端丢弃，也不会有人告诉调用方。
修复：`ProjectClient` 维护 `TaskState`（Dispatched/Failed/Done），超过协议窗口（1920s）仍无结果就报 failed；
`fetch_project_result` 返回 `status=failed` + `error`，agent 立刻带原因退出。

## 3. 下次怎么快速定位（不用猜）

```bash
# 一键分层：环境 -> 拓扑 -> VM 启动 -> 装工具链 -> 编译运行，每段计时
./scripts/diagnose_cluster.sh
```

手工等价步骤与判读：

```bash
# 1) 环境：KVM 权限、qemu 版本、bridge helper capability、bridge.conf、残留进程
ls -l /dev/kvm; id; qemu-system-x86_64 --version | head -1
getcap "$(command -v qemu-bridge-helper)"; cat /etc/qemu/bridge.conf
pgrep -af "target/debug/node"; pgrep -af qemu-system

# 2) 拓扑：n1 有没有 raft_id -> PeerId 映射（没有则 resolve_peer 直接失败）
grep -E "Connection established|Mapped raft id|Descriptor" /tmp/eo-diag/n1.log

# 3) 请求到没到执行节点（关键分水岭）
grep -hE "project task .* accepted|project result|Outbound project|Inbound project" /tmp/eo-diag/n*.log

# 4) 执行阶段卡在哪（本轮新增的日志）
grep -hE "qlean: (image|image ready|cold boot|reusing cached VM|upload|build|run)" /tmp/eo-diag/n*.log
```

判读表：

| 观察 | 结论 |
|---|---|
| 没有 `project task ... accepted` | 请求没到执行节点：连接/协议层问题，看 `Outbound project request failed` |
| 有 accepted，没有 `qlean: image ready` | 卡在镜像准备（下载/缓存） |
| 有 `cold boot start` 没有 `cold boot done` | 卡在 VM 启动：/dev/kvm 权限、bridge helper、QEMU 版本 |
| 有 boot done，没有 `build done` | guest 内部：apt 源/DNS/网络，或 build 命令本身 |
| 卡住时 `pgrep qemu-system` 为空 | VM 根本没起来，别去查 apt |

## 4. 平台门控代码的又一个坑（本轮新踩）

`crates/sandbox/src/qlean.rs` 的 Linux 实现开发机上从不编译，于是
`tracing::info!("... {} -> {parent}", dir)` 这种 **inline 命名捕获** 只在 Linux 上炸：

```
error[E0277]: `PathBuf` doesn't implement `std::fmt::Display`
```

原因是 `PathBuf: Display` 只在较新的 rustc 上存在，老工具链直接拒绝 `{parent}` 捕获。
结论：**凡是路径，一律显式写 `.display()` 作为参数**，不要用 inline 捕获。

尝试过的防复发手段与其局限（记录下来，避免下次白折腾）：

| 手段 | 结果 |
|---|---|
| `#[path = "../qlean.rs"]` / `include!("../qlean.rs")` harness | 能通过，但 cargo **不追踪被 include 的文件**：改 `qlean.rs` 不会让这个 bin 失效，检查静默通过（假阴性） |
| harness + 每次 `touch` | 能工作，但容易被忘记 |
| 临时把 qlean 加进 `[dev-dependencies]` | 可以，但为开发便利污染产品依赖清单，本轮已回滚 |

最终采取：**目标平台的 `cargo build` 才是唯一可信门禁**（`09-Phase1-bug归档.md` 的同一条结论）。

## 5. Linux 实测记录（两轮真实运行）

### 5.1 流水线本体全部正常（实测）

| 阶段 | 结果 |
|---|---|
| 环境 | `/dev/kvm` rw、用户在 kvm+libvirt、`qemu 6.2`、`bridge.conf: allow qlbr0` |
| 网格 | 25 条连接 + 25 个 raft-id 映射（3 节点满网格） |
| 镜像准备 | 31s |
| VM 冷启动 | **14.2s** |
| 上传 | **26-49ms** |
| 编译（`build_cmd=true`） | 42ms |
| 第二次任务 | `vm_cached=true` → `reusing cached VM`（VM 复用生效） |
| 执行节点 | 全部确定性落在同一节点（`on node c0ec6c68-…`） |

### 5.2 guest 网络是好的——真正的瓶颈是 Sources 索引

第二轮 stage B 在 guest 内探测的结果：

```
ens4            inet 192.168.221.138/24  (DHCP, 默认路由 192.168.221.1)
resolv.conf     nameserver 127.0.0.53 (systemd-resolved stub)
ping 10.0.2.2   100% packet loss          ← qlbr0 是 bridge 而非 QEMU user-net，10.0.2.2 本就不存在，误导项
getent hosts    deb.debian.org → 2a04:4e42:12::644   ← DNS 通
TCP 80          OK                                    ← 出口通
apt-get update  Get:7 …/debian trixie/main Sources [10.5 MB] → 60s 看门狗杀掉 → FAILED
```

**结论修正**：不是「guest 没有出口网络」，而是 `apt-get update` 在下载 **10.5 MB 的 `deb-src` Sources 索引**
（Debian cloud 镜像默认启用 deb-src）。在共享链路上这一步足以吃满任何预算，`-qq` 还让现场只剩一句
「build timed out」。

**修复（`crates/agent/src/main.rs::ensure_tool`）**：
1. 关掉 deb-src 索引：`apt-get -o Acquire::IndexTargets::deb-src::DefaultEnabled=false update`，不再下载 Sources；
2. **先试镜像自带的索引**（`apt-get install` 不带 update），失败才 update+install——命中时一次网络都不用发；
3. `-qq` 不再吞掉全部输出（首次尝试静默，回退路径保留输出）。

对应单测：`ensure_tool_avoids_source_indexes_and_tries_cache_first`。

### 5.3 本轮我自己的两个 bug（都已修）

1. **`./app` 找不到却报 exit 0**：`status.code().unwrap_or(0)` 把「被信号杀死 / 没有退出码」当成功。
   现在 `exit_code_of()`：有 code 用 code，被信号杀返回 `128+signal`（stage A 现在正确显示 exit 1）；
2. **诊断脚本的 bash 语法错误**：写了 `TMO=90 run_t() { … }`——**函数定义不能跟在赋值前缀后面**，
   guest 直接 `syntax error near unexpected token '('`（31ms 失败，exit 130）。
   现在函数统一定义在 `$GUEST_LIB` 里，调用形如 `TMO=180 run_t apt_install gcc`。
   本地验证方式：把生成的命令落到文件后 `bash -n`，并用 `TMO=2 run_t sleep 30` 确认看门狗语义
   （kill 后 exit 137，快速成功 0，快速失败 1，退出码透传）。

### 5.4 诊断脚本现在的四个阶段

| 阶段 | 目的 | 预期 |
|---|---|---|
| A | 只验 VM 启动 + 上传 + exec（`build_cmd=true`） | exit 1 + `./app: No such file`（**这是成功**） |
| B | guest 网络探测（ip/route/resolv/ping/DNS/TCP/apt×2，带看门狗） | 定位是网络还是索引 |
| C | 装 gcc（deb-src 关、180s 上限）+ 编译 + 运行 | `project-hello` |
| D | 完全复刻 eo-agent 现在生成的 `build_cmd` | `project-hello` |

## 6. 装工具链为什么慢，以及四层解决方案

### 根因（实测）

| 现象 | 数据 |
|---|---|
| guest 走 `deb.debian.org`（海外） | `apt-get update` 取 `trixie/main Sources` 10.5 MB，几分钟量级 |
| 云镜像默认启用 `deb-src` | 二进制装包根本不需要这份索引 |
| 复用 VM + 看门狗 `kill -9` | 残留 `/var/lib/apt/lists/lock`（held by process 970），后续 apt 全部 `Could not get lock`，毫秒级失败（exit 228） |
| `apt-get install` 不自己 update | 索引缺失时直接 `Unable to locate package`（exit 100） |
| stage D 我写错的分支 | `(run_t … && echo ok)` 失败时静默返回 0，外层 `&& gcc main.c` 被短路跳过 |

### 四层方案（按性价比排序）

| 层 | 做法 | 预期收益 | 状态 |
|---|---|---|---|
| **A. guest 换国内镜像源** | 探测可达性后把 `sources.list` / deb822 `.sources` 指向清华/中科大/阿里，探测失败回退默认源 | 索引与 deb 下载快 1~2 个数量级 | **已实现**（`MIRRORS` + `apt_mirror_setup()`） |
| **B. 宿主做本地 apt 缓存** | 宿主高速链路只下一遍，guest 走桥内网取包 | 首次之后接近零下载 | 待 stage C 的宿主测速结果决定 |
| **C. 预装工具链镜像** | 用 cloud-localds 打一个带 gcc 的模板盘，`ImageConfig` 指向它 | 彻底不装 | 规划中（`06-qlean集成阶段1.md` 原始方向） |
| **D. guest 借道宿主代理** | 网关是 `192.168.221.1` 而非 `10.0.2.2`；可指向宿主 Clash 的 http 端口 | 复用宿主代理 | guest 需先有 ca-certificates，鸡生蛋，暂不做 |

### 本轮同时修掉的三个坑

1. **锁残留**：`ensure_tool()` 先 `rm -f /var/lib/apt/lists/lock /var/lib/dpkg/lock{,-frontend}`；
2. **索引缺失时盲试 install**：改为 `set -- /var/lib/apt/lists/*Packages*` 判断，缺失才 update；
3. **`sed -i` 不可移植**：改成 `sed -i.bak … && rm -f "$f.bak"`。

### 验证方式（本机可复现，不需要 KVM）

`cargo test -p eo-agent print_ensure_tool -- --ignored --nocapture` 导出生成命令，再用假的
`apt-get`/`curl` + **隔离 PATH** 跑桩场景。**PATH 必须隔离**：本机自带 gcc 会让 `command -v` 短路，
第一次跑就得到三个假阳性。

| 场景 | 实测观察 |
|---|---|
| 无索引 + 残留锁 | 清锁 → `update`(deb-src off) → `install`，rc=0 |
| 工具已存在 | 零 apt 调用，rc=0（热路径仍是毫秒级） |
| 快源可达 | `apt mirror: https://mirrors.tuna.tsinghua.edu.cn/debian`，sources 被改写 |
| 快源不可达 | 回退 `http://deb.debian.org/debian`，不报错 |

## 7. 第三轮实测：guest 连网卡都没有（以及由此得出的自检机制）

### 现象

| 检查 | 第三轮结果 | 第一/二轮结果 |
|---|---|---|
| `ip -4 addr` | **只有 `lo`，没有 ens4** | `ens4 192.168.221.138/24` |
| default route | 空 | `via 192.168.221.1` |
| `getent hosts` | Temporary failure in name resolution | 正常解析 |
| `TCP 80` | Invalid argument | OK |
| `apt-get update` | 每个源都 `Temporary failure resolving` | 能下 10.5 MB Sources |
| 冷启动 | **131.8s** | 14.2s |
| 宿主测速 | 全部正常：deb.debian.org 9.6 MB/**1.57s**（6.1 MB/s）、中科大 1.88 MB/s | 同 |

**根因在宿主侧：qlbr0 桥不在了**（guest 的 ens4 是 QEMU 的 bridge NIC，宿主没有该桥，
guest 就没有网卡；DHCP 无从谈起）。这台机器上你之前手动修过三层权限
（`07-qlean验证排查记录.md` 第 5 条：helper cap、bridge.conf allow、用户组），
**而桥本身在重启/升级后会消失**——这正是「不可能每次启动都手动配」的场景。

### 两个被这轮放大的判定陷阱

1. **`apt-get update` 在所有源都解析失败时仍然 exit 0**（只打 `W:` 警告），
   所以脚本里那句 `APT-BIN/FULL UPDATE OK` 是假绿。已改为：先 `ip route` 查默认路由、
   再 `curl` 真实取 `Release` 文件，只有 HTTP 真的通才给 apt 判定；
2. **stage E 的 `set -- …; $1` 被外层 shell 提前展开**（`set -u` 直接 `$1: unbound variable`）。
   双引号包裹的脚本文本里，只有 guest 该展开的变量才用 `\$` 转义。已修。

### 由此新增的自动自检（解决「每次启动都要手动配」）

| 产物 | 作用 |
|---|---|
| `scripts/host_network_check.sh` | 宿主机网络自检：桥是否存在/有 IP、helper cap_net_admin+ep（并处理 suid 冲突）、`bridge.conf allow`、用户组、`ip_forward`、MASQUERADE、上游可达性。`--fix` 可自动修复（建桥、加 IP、setcap、改 bridge.conf、sysctl） |
| 节点启动 preflight（`crates/node/src/bootstrap.rs`） | 声明了 `project_sandbox: true` 的节点在启动时自检：`/dev/kvm` 存在与 rw、桥是否存在、helper 是否存在、`bridge.conf` 是否 allow、宿主到 Debian 源是否可达；任何一项不满足都直接 `warn!` **并打印修复命令**，而不是等任务静默空转 |
| `EO_MIRRORS` / `EO_BRIDGE` 环境变量 | 镜像列表与桥名有单一来源，不再散落在多处硬编码 |

设计原则：**宿主侧能查的都放在启动时查**（这些都是本地廉价操作），
guest 侧必须开 VM 才能查的（网卡、路由、DNS、apt）留在 `diagnose_cluster.sh`。

## 8. 仍然存在的边界（诚实记录）

- 单 qlean worker 串行执行，无 VM 池；节点重启即丢 VM，下一个任务仍是冷启动（历史实测冷 51.5s / 热 68ms）；
- 执行期间虽然事件循环不再被占，但同一节点上第二个项目任务会排队等 worker，`ProjectClient` 无并发调度；
- 快照仍以 tar_bytes 内嵌在协议里（上限 64MB），大项目应改为先推 CAS 只发 hash；
- `diagnose_cluster.sh` 只能在 Linux + KVM 主机上跑（qlean 平台门控）。
