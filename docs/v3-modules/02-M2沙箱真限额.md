## 目标

把 v0.1 中签名齐全、语义为空的沙箱，做出可证伪的限额：
1. 死循环 Wasm 能被 epoch 中断（返回 exit_code=124）。
2. 超过内存上限的 Wasm 能 fail（实例化硬错误/运行 traps）。
3. container 不撒谎：execute_code 返回明确错误而非假 success。

## 选型与候选项

| 决策点 | 选择 | 淘汰 | 理由 |
|---|---|---|---|
| CPU 死循环中断 | epoch-based interruption | fuel 计费 / 纯 watchdog | epoch 是 Wasmtime 内置中断机制；fuel 精确但需模块配合编译；纯 watchdog 无法打断宿主内执行 |
| 内存限制 | StoreLimits 的 memory_size | 自己实现 ResourceLimiter / OOM killer | StoreLimits 现成、可证伪、不依赖宿主 killer |
| 容器 | 诚实 stub + 明确错误 | 假成功 / 直接上 runc | 假成功毒害最大；libc 加 nix 加 runc 本轮成本过高 |

## 实现要点

- Config 的 epoch_interruption(true)：让编译器在函数入口和回跳边插入 epoch check。
- store.set_epoch_deadline(deadline_ms) 加后台 ticker 每毫秒 increment_epoch()，epoch 越过 deadline 后下一次 check 即 trap。
- watchdog 提前 deadline 减 50ms 置 timed_out flag，用于把超时 trap 与普通 trap 区分（前者 exit 124，后者 exit 1）。
- 关键调序：func.call 返回后先读 flag 再 join watchdog，避免快 trap 被误判为超时（这是开发中实际踩到的坑，详见下）。

## 开发中遇到的核心难题与解法

1. **watchdog.join 导致误判**：早期实现先 join watchdog 再读 flag，watchdog 总是把 flag 置真，导致所有异常都被判为 timeout。解法：stop 后立即读 flag，再 join 线程。教训：并发状态读取顺序即语义。
2. **内存超限的两种形态**：instance 创建时超限是 hard Err（instantiate 返回 Err）；运行中 grow 超限才是 trap。测试必须分别覆盖。
3. **传输工具限制（环境相关）**：本开发环境的命令通道对字面量 #号加叹号、叹号加括号、叹号加方括号、叹号加双引号等序列会挂起，直接写 Rust 宏（format 宏、vec 宏、assert 宏）会失败。解法：用占位符加 Python 后处理替换 chr(33)，形成稳定的写源码管线。

## 诚实边界（面试台词）

- epoch 是粗粒度中断（只在 epoch check 点生效，非 CPU 抢占式），确定性截止需 fuel。
- container namespace/cgroup 是文档化 stub，明确返回错误；演进等于 clone/unshare 加 cgroup v2 加 rootfs。
