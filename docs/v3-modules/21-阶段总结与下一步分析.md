# 阶段总结：从「pending 卡死」到端到端跑通

> 时间跨度：本项目这一阶段从「`verify_agent.sh` 提交后 540s 无响应」开始，
> 到 stage E 打出 `project-hello`（exit_code=0，60ms）结束。
> 本文归档**做了什么、实测数据、踩坑记录、剩余边界**，最后是**下一步工作分析**（仅分析，未实施）。

## 1. 起点：一个假象

现象：`./scripts/verify_agent.sh` 提交任务后 agent 一直 `still running...`，540s 后 Ctrl-C。
而 `task_id` 只证明「本地打包 + 选到节点 + 入队」成功，**不证明请求发出去了，更不证明有人在跑**。
整条链路上有 6 处静默失败路径，最终全部塌缩成同一个 `pending`。

诊断顺序（每一层都留下了可复现的判定）：

| # | 层 | 关键日志/证据 |
|---|---|---|
| 1 | agent | `--dry-run` 证明计划正确 |
| 2 | IPC + 路由 | `submit_project` 返回 task_id（说明 resolve_peer 成功） |
| 3 | swarm 命令 → 对端 | 新增 `accepted from <peer>` 日志，是「请求是否到达」的分水岭 |
| 4 | 对端事件循环 | 执行 inline 在事件循环上（致命缺陷，见 §3） |
| 5 | 执行器 + qlean | 新增 image/boot/upload/build/run 分阶段日志与超时 |
| 6 | 结果回传 | 新增 `result received` + `on node <uuid>` |

## 2. 端到端打通的最终数据（同一台 Linux + KVM + QEMU 6.2）

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 镜像准备 | 31-33s | 首次下载；后续复用 |
| VM 冷启动 | 14.2-14.8s | cloud-init |
| 上传快照 | 25-49ms | tar 内嵌协议（3584 B 示例） |
| 编译（`build_cmd=true`） | 42ms | |
| 冷路径首个任务（含装 gcc） | **48s（stage A）/ 96s（stage C）** | 提交 → 结果 |
| **热路径**（VM 复用 + gcc 已装） | **60ms** | stage E：eo-agent 的真实 build_cmd |
| 执行节点 | 确定性单节点 | `resolve_peer` 按 raft_id 最小选取 |

对比历史记录（`15-性能重构`）：冷 51.5s / 热 68ms —— 本轮热路径 60ms 与之同量级，
**冷路径的「装工具链」耗时从「不可预期（曾 300s 超时）」变成「受限于镜像源带宽的确定性开销」**。

## 3. 修了什么（按致命程度）

### 3.1 p2p：执行不再占住 swarm 事件循环（最致命）

原实现 `handle_project_exchange` 里直接 `executor.run(request).await`——项目执行是分钟级，
**期间该节点整个事件循环停摆**：descriptor / raft / blob 全冻结，连承载响应的连接都会被
60s idle 超时掐掉。

关键认知（绕了一圈才确认）：**「spawn 任务 + await oneshot」并不能解决**。
`ResponseChannel` 只是投递给 request-response handler 的 sender，响应必须由事件循环再次
poll swarm、调用 `Behaviour::send_response` 才写得出去。

最终方案：请求的 ResponseChannel 登记进 `pending: HashMap<TaskId, ResponseChannel<ProjectResult>>`，
任务在 detached task 上执行，完成后把结果回投事件循环，由事件循环统一写响应。

回归测试 `project_execution_does_not_block_the_swarm_event_loop` 用「慢执行器执行期间，已连接节点的
descriptor 请求必须被及时响应」锁死该不变量，并已验证：把执行改回阻塞式，该测试立即失败。

### 3.2 p2p：无 executor 的节点不再静默丢包

`if let Some(executor)` 原来没有 else——收下请求、什么都不做、不响应不报错，master 干等到
1800s 协议超时。现在回 `exit_code=101` + 原因，并 warn。

### 3.3 sandbox：全阶段超时 + 阶段日志 + 不撒谎的退出码

- image 300s / boot 600s / upload 300s / build+run 按剩余预算；超时明确报错并**丢弃 VM**（不复用坏 VM）；
- 每阶段开始/结束带耗时日志（这是后来定位瓶颈的唯一手段）；
- `status.code().unwrap_or(0)` → `exit_code_of()`：被信号杀死返回 `128+signal`。
  原来 `./app` 找不到会被报成 **exit 0**，把一个失败伪装成成功。

### 3.4 node：能力声明与真实能力一致 + 任务状态机

- 拿不到可用沙箱时，注册前把 `project_sandbox` 降级为 false（否则 master 永远路由到跑不了的节点）；
- `ProjectClient` 维护 `TaskState`（dispatched/failed/done）+ 1920s 兜底；
  `fetch_project_result` 返回 `status=failed` + `error`，agent 立刻带原因退出而不是轮询到 30 分钟。

### 3.5 agent：装工具链的可用性（这一阶段最后一块拼图）

`ensure_tool()` 生成四件事同时具备的命令：

1. **探测并换国内镜像源**（清华/中科大/阿里，不可达则回退默认）；
2. **永久关闭 deb-src 索引**（`Acquire::IndexTargets::deb-src::DefaultEnabled=false`，省掉 10.5 MB 的 Sources）；
3. **清理残留 apt/dpkg 锁**（复用 VM 里被超时杀死的 apt 会留下锁，后续任务毫秒级 `Could not get lock`）；
4. **索引缺失才 update**（`apt-get install` 不自己 update，否则 `Unable to locate package`）。

### 3.6 运维：启动自检 + 自动修复（本轮新增）

| 产物 | 作用 |
|---|---|
| `scripts/host_network_check.sh` | 宿主自检：桥存在/IPv4、helper `cap_net_admin+ep`（并处理 suid 冲突）、`bridge.conf allow`、用户组、`ip_forward`、MASQUERADE、上游可达性；`--fix` 自动修复 |
| `scripts/preflight.sh` | 被两个验证脚本 source 的前置门：健康 → 放行；不健康 → 尝试 `sudo -n --fix` 自动修复；无免密 sudo 则**打印命令并中止**（不卡在密码提示） |
| 节点启动 preflight | 声明 `project_sandbox: true` 的节点，启动即自检 `/dev/kvm`、桥、helper、bridge.conf、宿主到源可达性，任一不满足直接 warn + 给出修复命令 |

**设计原则**：宿主侧能查的全部前移到启动时（本地廉价操作）；必须开 VM 才能查的（网卡、路由、DNS、apt）
留在 `diagnose_cluster.sh` 的 guest 探测阶段。

## 4. 踩过的坑（全部归档，避免重复）

| # | 坑 | 教训 |
|---|---|---|
| 1 | `tracing` 的 `{parent}`（PathBuf）只在目标平台编译失败 | 路径一律显式 `.display()`；cfg 门控代码必须目标平台编译 |
| 2 | `#[path]`/`include!` 做的 Linux 路径检查是**假阴性** | cargo 不追踪被 include 的文件，静默通过旧产物；目标平台 `cargo build` 才是唯一可信门禁 |
| 3 | `TMO=90 run_t() { … }` 非法 bash | 函数定义不能跟在赋值前缀后；生成的 guest 命令要 `bash -n` + 桩环境验证 |
| 4 | `(cmd && echo ok)` 在 `\|\|` 右侧静默成功 | 失败分支不能只写 `&& 成功提示`，否则外层 `&&` 被短路、错误被吞 |
| 5 | 看门狗 `kill -9 apt` 污染复用 VM | 杀 apt 要配套 `reap`（杀进程 + 清锁）；否则后续任务全 `Could not get lock` |
| 6 | `apt-get update` 全源解析失败仍 exit 0 | 判定必须基于真实 HTTP 取文件 + 默认路由，不能信 apt 退出码 |
| 7 | 双引号脚本文本里 `$1`/`$MIRROR` 被**外层** shell 提前展开 | `set -u` 直接 `$1: unbound variable`；guest 该展开的变量要 `\$` 转义 |
| 8 | 桩测试用本机 `gcc` 导致假阳性 | 验证「工具不存在」的路径必须隔离 PATH |

## 5. 剩余边界（诚实记录）

- 单 qlean worker 串行执行，无 VM 池；**同一个 VM 的系统盘在任务间共享**——这是我们被迫清 apt 锁的根源，也意味着任务之间不隔离；
- 节点重启即丢 VM，下一个任务仍是冷启动；
- 快照以 tar_bytes 内嵌在协议里（上限 64MB），大项目必须改成先推 CAS；
- 结果表是 `HashMap`（内存态），节点重启即丢，无任务级查询接口；
- `ProjectTask` **不走 raft 调度**（`runtime_loop` 只处理 Wasm 的 `ScheduledTask`），
  所以 `role_engine`/`scheduler`/reroute 这条分布式叙事链路在项目场景下是「死的」；
- LLM 规划/分析路径仍无 API key，未实测；
- 轻客户端 master（`Catalog::Peers`）路径在本轮改动后未回归。

## 7. 下一步工作分析（仅分析，未实施）

### 6.1 优先级排序（按「面试价值 × 当前缺口」）

| # | 工作 | 为什么值得做 | 大致代价 |
|---|---|---|---|
| 1 | **快照走 CAS 分发**（只发 hash，执行节点按需拉取） | 现在 64MB 内嵌是硬上限；`ProjectSnapshot.hash` 已预留、`BlobExchange` 已有协议与 `RequestBlob` 命令，**这是设计里唯一没落地的关键链接**。也是分布式存储叙事的收口 | 中（协议改 hash 传递 + 执行端 CAS miss 时拉取 + 幂等） |

| 4 | **持久化任务结果 + 查询接口** | 现在重启即丢；生产语义应有「任务状态可查、可追溯」 | 低（结果落 CAS + 索引） |

### 6.2 判断依据

- 1、2 是**把已有设计补完**（协议已留 `hash` 字段、blob 通道已存在、角色引擎已写好），
  属于「投入产出比最高、且直接强化项目主线叙事」的部分；
- 3 是**从"能跑"到"敢叫沙箱"**的分界线，而且顺手解决一类已实际发生的故障；
- 5 属于纯性能，且当前热路径已经 60ms，**只有在「首次任务耗时」成为瓶颈时才值得做**；
- 7 是安全边界，若要在简历/答辩中强调「隔离」则必须做，否则会被追问「guest 能出网还算沙箱吗」。

### 6.3 建议的下一阶段目标（供选择）

- **方案 A（推荐）**：1 + 3 —— 完成 CAS 快照分发 + 每任务独立系统盘。
  产出：任意大小项目可执行；同一 VM 内任务互不影响；可讲清「分发 + 隔离」两条主线。
- **方案 B**：2 + 4 —— ProjectTask 接入 raft 调度 + 结果持久化。
  产出：控制面统一，节点故障可 reroute，可演示「杀掉执行节点任务自动重分配」。
- **方案 C**：5 + 6 —— 性能与可观测性收口，把冷路径压到 10s 内并给出百分比图。

三者都可与「面试叙事」对应：A→存储与隔离，B→分布式共识与控制面，C→性能工程。
