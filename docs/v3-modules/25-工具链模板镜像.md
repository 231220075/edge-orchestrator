# 工具链模板镜像：让 `fresh` 模式真正可用

> 问题：`fresh`（每任务一台 machine）给了隔离，但**池里的机器是从基础镜像新启动的空机**，
> 不带工具链。于是需要 `gcc` 的任务在 fresh 模式下每次都要 `apt install`（实测约 96s）。
> 池化只拿掉了"启动等待"，拿不掉"装工具链"。

## 1. 唯一正确的解法：预装工具链的模板镜像

`seal` 之后，`fresh` 的代价从「启动 14s + 装工具链 ~96s」降到「启动 14s（可被池化隐藏）」，
而且**仍然每任务独立磁盘**——隔离与速度不再互斥。

## 2. 配置（已实现，代码侧打通）

```yaml
capabilities:
  project_sandbox: true
  project_vm_mode: fresh            # 隔离模式
  project_vm_pool_size: 1           # 预热 1 台，隐藏启动等待
  project_image_source: /var/lib/eo/toolchain.qcow2   # 模板镜像（URL 或本地路径）
  project_image_digest: sha256:<hex>                  # 必须提供，qlean 会校验
```

约束来自 qlean 的实现（`Image::new`）：**只有同时给出 source 和 digest 才会去取自定义镜像**，
否则回落到内置远程镜像。所以 digest 不是可选项——本项目对配置做了前置校验：

| 配置情况 | 行为 |
|---|---|
| 两者都缺 | 用内置镜像（默认） |
| 只给 source | **启动时 warn 并忽略**，不会去猜 digest（猜了等于关掉校验） |
| digest 格式非法（不是 `sha256:<hex>` / `sha512:<hex>`） | 启动时 warn 并忽略 |
| 两者齐全 | 使用模板，启动日志显示 `base_image=<source>` |

单测覆盖：`ImageTemplate::from_config`（缺 digest、缺 source、非法 digest、合法模板）、
节点配置解析与回退（`crates/node/src/config.rs`）。

## 3. 构造模板镜像（需要宿主机有 KVM，**尚未在本项目实测**）

思路是「用 qlean 自己造这个模板」：先起一台 VM，在里面装好工具链，再把它的 overlay 磁盘
抽出来当作模板。

```bash
# ① 起一台一次性 VM（用项目自己的沙箱，或直接用 qlean 的小 demo）
cargo run -p qlean-project-demo            # 见 scripts/qlean-project-demo

# ② 找到它的 run 目录与 overlay 盘
ls -lt /var/lib/qlean/runs/ | head         # 最新一个 machine_id
#   <runs>/<id>/overlay.img  ← 这台 VM 的可写层，已经装了 gcc

# ③ 把它拷出来，卸掉 backing file 依赖，得到独立镜像
sudo qemu-img convert -O qcow2 -U \
  /var/lib/qlean/runs/<id>/overlay.img /var/lib/eo/toolchain.qcow2
sudo chown $USER /var/lib/eo/toolchain.qcow2

# ④ 关闭这台 VM（不要让它继续持有该盘），然后取 digest
sha256sum /var/lib/eo/toolchain.qcow2

# ⑤ 写进节点配置
#   project_image_source: /var/lib/eo/toolchain.qcow2
#   project_image_digest: sha256:<上一步的 hex>
```

要点与坑：

- **必须 `qemu-img convert`**（或 `-b` 关系显式保留）：直接把 `overlay.img` 当模板，
  它仍然依赖原基础镜像的 backing file；`convert` 会把它拍平成独立镜像；
- 模板镜像里的 guest 需要**沿用 cloud-init + 与 qlean 相同的 sshd socket 激活**方式，
  否则 qlean 起不来（本步骤最容易出问题的地方）；
- 模板应当只包含"通用工具链"（gcc/make/cargo/…），**不要**包含某个项目的产物。

## 4. 验证模板生效

`scripts/diagnose_cluster.sh` 的现有阶段即可判定：

| 观察 | 含义 |
|---|---|
| 节点启动日志出现 `base_image=/var/lib/eo/toolchain.qcow2` | 配置已生效 |
| stage D/E 的 `executed_ms` 从 ~96000ms 掉到 ~15000ms 量级 | 模板里已有工具链，没再装 |
| stage G 打印 `MARKER-GONE` | 仍然是每任务独立磁盘（隔离未被破坏） |

## 5. 诚实边界

- **第 3 节的操作没有在本项目里实测**：本机（macOS）没有 KVM，无法起 VM 造模板，
  也无法验证模板镜像能否被 qlean 正常引导。代码侧的配置路径有单测，
  但"模板镜像本身能不能用"只能由你在 Linux+KVM 主机上验证；
- 因此我没有伪造 digest、也没有把默认配置指向一个不存在的镜像——配置缺省仍是内置镜像；
- 模板一旦确定，**升级工具链需要重建模板并更新 digest**（这是"不可变基础镜像"的常规代价）；
- 池化目前只保留 1 台空闲机（worker 串行）；要多任务并行需要 worker 线程池。
