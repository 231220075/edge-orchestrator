## 1. 三个灵魂问题（最终回答）

### Q1 需不需要自组网？
**不需要自研。** 用 libp2p 已配置好的 mDNS + Noise + Yamux 即可；补一个 **固定 IP 的手动 bootstrap peer** 作为 mDNS 失败时的保命兜底（macOS 防火墙/公司 WiFi 下 mDNS 经常静默失败）。

### Q2 需不需要分布式？
**需要，且必须是"有意义的分布式"。** 这是 v3 的主线：把 Raft 从"单节点装样子"变成"3 节点真一致性 + kill leader 自愈 + 任务重路由"。没有这条，其他全都没意义。

### Q3 需不需要微服务？
**绝对不需要多进程/微服务。** 采用 `单二进制 node`，内部按 trait/模块分层。合并 crate 时注意：**"合并 crate" ≠ "删除模块"**，搬到 `node/src/` 下的模块仍要保留可单测性。

## 2. 架构分层（v3 目标）

```
┌──────────────── 触发层（可裁剪）────────────────────┐
│  Mac CLI  ──UDS/JSON-RPC──┐                          │
│  iPhone   ──HTTP/JSON-RPC──┤  → Gateway(trait TaskSubmitter)   │
│  (M5 可选) ────────────────┘                          │
└───────────────────────────────┬──────────────────────┘
                                │ JSON-RPC 2.0（UDS/HTTP 同 handler）
┌───────────────────────────────▼──────────────────────┐
│  node 单二进制（Rust）                                 │
│  ├─ 控制面：Raft(RawNode) —— 节点表 + 任务路由表        │
│  │      └─ transport：libp2p（raft 消息 + blob 分发同走）│
│  ├─ 调度：scheduler + role_engine（node 内部模块）      │
│  ├─ 数据面：CAS 存储（Git 模型，复用 storage crate）    │
│  │      └─ P2P blob 分发（request-response /eo/storage/1）│
│  └─ 执行：Sandbox trait（Wasmtime 真限额 / container stub）│
└───────────────────────────────────────────────────────┘
```

**叙事主线（面试一句话）：** 控制面 Raft 保证元数据 CP，数据面 CAS 保证去重与 AP，libp2p 做设备无关传输，沙箱做不可信代码的隔离执行。

## 3. 完整技术选型框架（含开发语言、三方库、持久化）

### 3.1 总表（一页速查，面试可背）

| 决策点 | 选型 | 主要候选 | 淘汰理由（一句话） |
|---|---|---|---|
| 开发语言 | **Rust**（保留）+ **Python 仅残留薄客户端/测试** | Go / Zig / C++ | Rust 已有全部资产；所有权模型天然适合写沙箱边界 |
| 异步运行时 | **tokio（multi-thread）** | async-std / smol | 生态绑定 libp2p/wasmtime/axum 均首选 tokio |
| 网络组网 | **libp2p**（mDNS+Noise+Yamux+request-response+gossipsub） | 裸 TCP+自研协议 | libp2p 提供开箱即用的加密/多路复用/发现，自研有安全审计成本 |
| 一致性与选主 | **tikv/raft-rs RawNode（raft 0.7）** | Paxos、etcd 嵌入、自研 | Paxos 难工程化；etcd 是外部组件引入运维面；raft-rs 已有资产 |
| 序列化 | **serde + JSON**；二进制可选 bincode | protobuf/prost（应用层） | Proposal 已用 serde；应用层 protobuf 要额外 schema 成本，收益低 |
| 持久化（Raft 日志/状态） | **复用 storage crate 的 CAS**（写入 raft 目录前缀） | RocksDB/sled/etcd WAL | 已有 CAS 资产，对象模型天然适配快照；引入 RocksDB 是重依赖 |
| 持久化（节点配置/元数据） | **YAML 配置文件 + CAS 快照** | SQLite/etcd | 元数据量级小、需人类可读；SQLite 强绑定单机不优雅 |
| 沙箱（Wasm） | **wasmtime 45**（Engine/config/StoreLimits/epoch） | wasmer、wazero、wasm3 | wasmtime 与 Rust 互操作最好，已有资产；wasmer 商业版本碎片化 |
| 沙箱（Container） | **Linux namespaces + cgroup v2（实现为 stub 或引入 libc/nix）** | Docker SDK、runc/libcontainer | Docker 是引擎非库；libcontainer 绑定成本高，本轮先说明性 stub |
| 进程间 IPC（本机） | **UDS + JSON-RPC 2.0**（保留） | gRPC over UDS | 复用现有 handler，零迁移成本 |
| 跨设备（iPhone） | **HTTP + JSON-RPC 2.0（axum 0.7/0.8）**，Tailscale 兜底 | 见 `05-iPhone通信可行性评估.md` | 见该文档 |
| LLM Agent | **薄 prompt→JSON + JSON Schema 校验**（砍 LangGraph） | LangGraph/多智能体 | AGENT_PLAN.md 的 Token 爆炸论；确定性流程不需图框架 |
| 日志/可观测性 | tracing + tracing-subscriber（env-filter） | println/log | 已用 tracing，可开关区间日志，demo 要能看到 raft 状态 |

### 3.2 开发语言与运行时（为什么继续 Rust）

- **候选对比**：
  - **Go**：协程模型对长连接网络服务友好，但已有 storage/p2p/sandbox 是 Rust，迁移=重写，放弃最大资产；
  - **Zig/C++**：性能极佳但生态/内存安全成本高，不适合面试效率优先的项目。
- **结论**：Rust + tokio。所有三方库（libp2p、wasmtime、ada）都以 tokio 为首选 runtime，选 async-std/smol 会造成双重 runtime 依赖地狱。

### 3.3 持久化的最终选择（重点答疑）

**结论：不引入 RocksDB/sled/SQLite，持久化统一走 storage crate 的 CAS。**

理由与分场景：

| 数据 | 存哪 | 说明 |
|---|---|---|
| 代码 blob / 执行结果 | CAS `objects/` | 内容寻址去重 |
| Raft 日志 + 快照 + term/voted_for | CAS 的 raft 目录前缀（复用 `CasRaftStorage`，当前用 temp 目录，需改成 `$EO_HOME/raft`） | 避免新增存储引擎 |
| 节点描述符/角色 | 内存 HashMap（启动时由 Raft state machine 回放恢复） | 由 Raft 日志恢复，无需独立 DB |
| 配置 | YAML（configs/*.yaml） | 人类可读，启动时加载 |

- **为什么不用 RocksDB/sled**：元数据量级只有几十 KB~MB 级，上 LSM 引擎是过度工程；且 Raft 快照机制下 CAS 的对象模型足够。
- **诚实的边界**：如果未来节点数扩大到上千、任务量到百万级，需要换 RocksDB 做热元数据 + CAS 做冷数据，v3 不提前做这个拆分。

### 3.4 沙箱选型（本版本最需务实的一处）

**决策：Wasmtime 为主，container 降级为"说明性 stub + 明确台词"。**

| 沙箱 | v3 实现程度 | 面试台词 |
|---|---|---|
| Wasmtime | **真实现**：线性内存隔离 + StoreLimits（内存上限）+ epoch-based interruption（死循环/超时） | 讲清"隔离 vs 限制"三层 |
| Linux container | **stub**：保留 trait 签名，`execute_code` 返回明确的 UnsupportedPlatform/stub 错误 | 老实说"namespaces 隔离什么、cgroup 限制什么、边界在哪"，以及"为什么 v3 不做真实现（需 libc/nix + rootfs）" |

**为何 container 降级**：源码 container.rs 是 0% 实现，真做 namespace+cgroup 需引入 libc/nix 或 runc 绑定，至少 5 天，且面试风险高（容易被打穿）。把时间换给 M3 自愈主线。

## 4. 模块合并方案（8 → 4，每步落到文件）

| 原 crate | 目标 | 文件映射 |
|---|---|---|
| core | 保留 `crates/core` | 原样 |
| storage | 保留 `crates/storage` | 原样，仅改 transport.rs |
| sandbox | 保留 `crates/sandbox` | 原样，改 wasm.rs + 补充 epoch/limit |
| p2p | 保留 `crates/p2p` | 新增 raft 消息 + blob 分发协议 |
| raft | 合并进 `crates/node/src/raft/` | 保留 node.rs/state_machine.rs/proposal.rs/storage.rs，重写 network.rs 为 libp2p transport |
| orchestration | 合并进 `crates/node/src/scheduler/` | role_engine.rs/scheduler.rs/topology.rs 原样搬入 |
| ipc | 合并进 `crates/node/src/gateway/` | handler.rs/server.rs 搬入；新增 http_server.rs |
| node | 保留 `crates/node`（唯一二进制） | bootstrap.rs 大改接线 |

**合并后的最终 crate 列表**：`core`、`storage`、`sandbox`、`p2p`、`node`（5 个，比 plan-v2 的 4 多保留一个 p2p，因为 p2p 是网络边界，独立更利于测试 + 面试讲得清；若你坚持 4 个，可把 p2p 并入 node，但我不推荐）。

### 4.1 合并动机（面试可讲）

v0.1 的错误不是"crate 多"，而是"crate 边界与运行时生命周期错配"：p2p 与 raft 必须同生命周期、互相转发消息，拆成两个 crate 后中间只能靠 mpsc stub 糊住。v3 把它们收敛到一个进程内的模块，边界落在 trait 上，比假装微服务更诚实。

## 6. M3 真·分布式 的关键设计（v3 的重中之重，AI 开发避坑表）

### 6.1 Raft node_id ↔ PeerId 映射

- 启动时每个节点生成 `uuid v4` node_id + ed25519 keypair→PeerId；
- 通过 descriptor 交换协议建立映射：发现 peer → 收到 descriptor（含 node_id）→ 写入 `PeerRegistry{node_id: PeerId}`。
- **最终 `RaftEnvelope` 发送时：`raft_node_id` → 查 `PeerRegistry` → `swarm.behaviour_mut().raft_request_response.send(peer_id, msg)`**（替代现有 mpsc stub）。

### 6.2 Raft 消息协议（选型：gossipsub 广播 + request-response 点对点兜底）

- **gossipsub**：用于 Raft 心跳/投票/Append 的广播（数据面）；局域网丢失率低，加 from/to 过滤即可；
- **request-response**：用于大 payload（如快照/大 blob）点对点可靠传输；
- **为什么不能只靠 mDNS**：mDNS 只是发现不是消息传输；现在 `swarm.rs` 只处理 descriptor 交换。

### 6.3 任务重路由（最容易翻车处）

- **关键认知：raft-rs 只保证日志一致，不保证任务被谁执行。**
- 设计：任务提交 → Raft 提交 `SubmitTask` → state machine apply 时把任务写入 `pending_queue`（**而非立刻路由**）→ 调度器从 pending 拉取并指定 executor → 若 executor 心跳超时/failure，**把任务重新放回 pending**（在 state machine 的 `handle_node_failure` 里做）。
- **涉及成员变更的部分一律 stub**：v3 只做静态 3 节点，`AddNode/RemoveNode` 挂在"未来工作"，面试诚实说"joint consensus 未实现，成员变更走手动重启"。

### 6.4 验收证据链三段式

```
启动 3 节点（Mac + Linux VM + 任意第三台）
→ 提交任务，观察 raft 日志复制到 3 节点（tracing 打 term/index）
→ kill -9 leader
→ 观察剩余节点 election_timeout 内选出新 leader（日志 raft_state=Follower→Candidate→Leader）
→ 观察死者节点未完成的任务被重新路由到存活节点并执行成功
→ 输出「故障 → 重选主 → 任务重路由」三段式。
```

## 7. M2 沙箱补强的实现要点（含陷阱预警）

### 7.1 Wasmtime 真限额的最小实现

```
Config::new()
  .wasm_multi_memory(true)          // 如需要
  .epoch_interruption(true)          // 开启 epoch
  .store_limits_2(StoreLimitsBuilder::new().memory_size(...).build())  // 内存上限
```
- 死循环中断：spawn 一个后台 timer，到期调用 `store.epoch_deadline_trap()`，使在 epoch 边界抛 trap；
- **陷阱预警**：若死循环是纯计算且无 import 调用，epoch 中断**只能在下个 epoch 检查点生效**——这正是面试追问点，要能口述 "epoch 是 tick 边界，不是 CPU 抢占"。

### 7.2 Container stub 的正确"诚实"实现

```
execute_code(...) -> Err(UnsupportedPlatform/Stub(...))  // 明确错误，而非假 exit_code=0
```
（v0.1 返回假成功是最大毒奶茶 —— 面试一定会抽测到。）

## 8. AI 辅助开发协议（给 AI 助手看的任务规范）

1. **永远先跑可复现命令**：`cargo build --workspace` / `cargo test -p xxx` / `cargo clippy --workspace --all-targets -- -D warnings` / `cargo fmt --check`，贴原始输出；
2. **每个里程碑给 AI 三条验收**：build 通过 / 特定测试通过 / 某个 demo 命令可跑；
3. **可证伪优先**：沙箱要"死循环/OOM 测试"；分布式要"kill leader 的脚本"；不接受"看起来对了"；
4. **commit 粒度**：M1 搬模块一个 commit；M2 每个沙箱能力一个 commit；M3 每个阶段（映射→协议→重路由）一个 commit；
5. **不碰的禁区**：成员变更 stub；container 真实现（除非明确授权）；性能优化（除非测试证明瓶颈）。

## 附：一句话总结

v3 = 砍掉伪装税（8→5）、沙箱只把 Wasm 做到真限额（container 诚实 stub）、把 Raft 真正接上 libp2p 并做出 kill-leader 自愈证据链、agent 缩成 prompt→JSON。
**主线只有一个：证明 v0.1 做不到的"故障自愈"，在 v3 里真的发生。**
